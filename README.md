# MedSim Case Review Portal

A web application built for a joint research project between the **Faculty of
Medicine** and the **Faculty of Education** at the **Technion**, supporting
the **MARAK** course ("Introduction to Clinical Medicine"). It lets
supervising physicians review medical-student simulation sessions — each
session is a chat conversation between a student and an AI-driven **virtual
patient** — and score them using three structured questionnaires.

The whole application (UI, questionnaires, and this document) is in
**English only**, as required.

---

## 1. What this application does

- **Doctors** log in and see a list of **cases** (virtual patients). Each
  case has a number of **sessions** — recorded conversations between a
  medical student and the virtual patient, generated by the MedSim
  platform.
- Opening a session shows, in order:
  1. The virtual patient's details (case name, date, duration, tests
     performed, hints used, student score).
  2. The full chat transcript between the student and the virtual patient.
  3. **Questionnaire 1** — about the virtual patient's realism/behavior.
  4. **Questionnaire 2** — about the student's performance (1–10 scales).
  5. Once **both** questionnaires above are fully answered, the **AI-generated
     feedback** that was shown to the student is revealed, followed by:
  6. **Questionnaire 3** — about the quality of that AI feedback.
- Every answer **auto-saves** as the doctor fills it in — there is no
  "submit" button to remember to click.
- Each session shows a colored status the doctor can track at a glance:
  - 🟢 **Green** — fully handled (all 3 questionnaires completed)
  - 🟡 **Yellow** — in review (started, not yet complete)
  - ⚫ **Black** — not handled yet
- **Doctors only ever see their own review progress and answers.** They
  cannot see what other doctors wrote.
- **Student emails are never stored, displayed, or exported anywhere** in
  the system — they are stripped out the moment a CSV is imported.

### Admin panel

The administrator (`username: admin`) has a separate panel to:
- View overall statistics and each doctor's progress (green/yellow/black
  counts, completion %).
- Add, edit, and remove doctor accounts (name + username; the shared
  password `1234` is set automatically).
- Upload/replace the case data by importing the MedSim CSV export.
- Download all collected questionnaire data (for research analysis) as
  **JSON** or **CSV** — with student emails always excluded.

## 2. Running the project locally (Node.js)

**Requirements:** Node.js 18 or newer (Node 20+ recommended) and npm.

```bash
# 1. Install dependencies
npm install

# 2. Start the server
npm start
```

Then open **http://localhost:3000** in your browser.

That's it — **no manual file editing is required.** On first launch the
server automatically:
- Creates `data/admin.json` and `data/doctors.json` (with the demo accounts
  above),
- Creates `data/responses.json` (empty, ready to store answers),
- Imports the bundled `data/seed-source.csv` into `data/cases.json` so the
  app has real cases to show immediately.

To change the port, set the `PORT` environment variable:
```bash
PORT=8080 npm start
```

## 3. Data storage

All application data is stored as **local JSON files** on the server, under
`/data`:

| File | Contents |
|---|---|
| `admin.json` | The single admin account |
| `doctors.json` | All doctor accounts (id, name, username, password) |
| `cases.json` | All virtual-patient cases and their sessions (imported from CSV) |
| `responses.json` | Every doctor's questionnaire answers, keyed by `doctorId__sessionId` |
| `.session-secret` | Auto-generated signing secret for login tokens (do not commit) |

Writes go through a small in-process queue (`server/lib/store.js`) so
concurrent requests never corrupt a file, and each write is atomic (written
to a temp file, then renamed).

These generated files are excluded from git via `.gitignore` (only the
seed CSV and the code are committed) — so a fresh clone always starts from
a clean, working state.

## 4. Importing / re-importing case data (CSV)

The **Admin → Case Data & Export** tab lets the administrator upload a new
CSV export from the MedSim platform at any time. This **replaces** the
current case list; doctors' saved questionnaire answers are kept (they are
stored independently, keyed by session ID).

Expected columns (as produced by the MedSim export):

```
id, user_id, messages, diagnosis, timestamp, title, review, score,
chat_duration, tests_asked, requested_tests, hints_used, case_uuid, email
```

- `messages` — JSON array of the chat transcript (`role`, `content`, `timestamp`).
- `review` — JSON object with the AI feedback given to the student
  (`overall_score`, `summary`, `categories[]`, `correct_diagnosis`, ...).
- `case_uuid` — sessions sharing the same `case_uuid` are grouped into one case.
- `email` — **always discarded on import** and never stored.

## 5. Deploying to Firebase (optional)

You mentioned wanting to run this locally first (`npm start`) and later
deploy it to Firebase — that workflow is fully supported.

**Important storage note:** this project stores its data as local JSON
files on disk, exactly as required. That works perfectly with `npm start`
on your own machine, a VM, or any host with a persistent disk. Plain
**Firebase Cloud Functions**, however, only provide *ephemeral* storage —
files can be wiped whenever an instance recycles. So for a Firebase
deployment, pick one of:

1. **Firebase App Hosting** (recommended if you want to stay in the
   Firebase ecosystem) — runs a real, persistent Node.js backend (Cloud Run
   under the hood), so the local-JSON-file approach keeps working as-is.
2. Keep running the included Node server on your own infrastructure /
   Cloud Run with a mounted persistent disk.
3. Use the included `functions/` + `firebase.json` for **Firebase Hosting +
   Cloud Functions** — good for a quick public demo, but be aware saved
   answers may not persist reliably between requests.

To try the Cloud Functions path:
```bash
npm install -g firebase-tools
firebase login
# edit .firebaserc and set your real Firebase project ID
firebase deploy
```

The `public/` folder is served as Firebase Hosting, and every `/api/**`
request is rewritten to the `api` Cloud Function, which loads the exact
same Express app used locally (`server/app.js`) — so there is nothing to
keep in sync between the two environments.

## 6. Privacy note

Per the project requirements, **student email addresses are never shown in
the UI and never included in any export.** They are dropped during CSV
import (`server/lib/csvImport.js`) and are not present anywhere downstream.
